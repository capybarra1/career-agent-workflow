# Resume Writing

## 目标

把用户的真实经历转化为与目标岗位相关、具体且可核验的简历证据。事实与个人产出优先，不用固定流程词代替内容。

## 必读资料

- 任何撰写或改写：完整读取 [写法规则](references/writing-patterns.md)。
- 整份诊断、JD 定向改写或最终质检：同时完整读取 [评分标准](references/scoring-rubric.md)。

## 输入

必填：

- 目标岗位、岗位库中的选定记录或完整 JD；
- 个人求职信息库链接。

可选：现有简历、页数、语言、隐私限制、希望强化或删除的内容。

## 飞书事实读取

1. 解析个人信息库链接，读取当前真实表结构。
2. 只使用个人档案、教育经历、实习经历、经历素材、项目经历、技能与工具、目标岗位、荣誉奖项。
3. 最终正文只使用标为已确认或由用户在当前对话明确确认的事实。
4. 待补充、待确认、冲突或不可外发内容只进入事实台账，不进入终稿。
5. 从推荐岗位明细读取目标岗位时，同时读取关联公司、JD、匹配点和主要短板；也可接受用户粘贴的 JD。

## 默认工作流

### 1. 明确目标与边界

确认目标岗位、候选人阶段、页数或字数、隐私限制和希望强化的内容。没有完整 JD 时，按岗位方向生成通用版本并明确适用范围。

### 2. 建立岗位—证据映射

提取核心任务、必备能力、结果期待、行业与工具门槛。逐项映射到个人信息库事实，并标为强证据、弱证据或缺失证据。

### 3. 建立事实台账

按经历记录：场景/需求、个人措施、个人产出、效果证据、责任边界、项目状态和事实状态。

### 4. 重建项目边界

同一业务目标、同一对象且共享连续交付链路的素材合并；目标、对象、问题或交付物不同的项目分开。整段经历统一采用项目、产品模块或关键成果中的一种层级。

### 5. 执行信息充足度门槛

核心条目必须同时具备：具体场景或问题、本人关键措施/交付物、可核验结果或明确里程碑。缺一项时先输出缺失信息表并追问，不把泛化文字称为终稿。

### 6. 深挖量化与闭环

按业务结果、用户价值、质量、效率、规模、交付或决策动作依次寻找证据。数字要说明对象与口径；无法确认数字时使用最强的非数字证据。

### 7. 成稿与排序

按岗位相关性 × 证据强度 × 结果价值排序。经历倒序，最强证据靠前；每条尽量只证明一个主结论。

### 8. 质检

检查岗位匹配、场景具体性、个人所有权、专业判断、结果口径、项目状态、时间逻辑和敏感信息。整份简历按 30 分标准评分。

## 写作红线

- 不编造经历、数字、工具、技术细节、项目状态或个人所有权。
- 不把团队结果写成个人全部贡献。
- 不把计划、原型、Demo、POC、UAT、测试或灰度写成正式上线。
- 不使用无法解释对象、基线、时间或口径的百分比。
- 不因匹配 JD 添加未做过的技能、行业或职责。
- 不把同一项目的不同阶段拆成重复项目，也不因关键词相似而合并不同项目。
- 不用“提供依据、支撑决策、赋能业务、推动发展”等抽象影响替代具体产出。

## 输出

信息充分时输出：

1. 关键诊断与修改策略；
2. 可直接使用的 Markdown 简历；
3. 供排版使用的结构化 JSON；
4. 必要的事实与口径说明；
5. 六维评分和剩余缺口。

建议 JSON 顶层结构：

```json
{
  "profile": {},
  "education": [],
  "experience": [],
  "projects": [],
  "skills_and_honors": [],
  "target_job": {},
  "quality_review": {}
}
```

信息不足时输出：当前可确认判断、缺失数据表、3–8 个高价值问题，并明确补充后继续。用户明确要求保守版时可先输出，但必须说明证据上限。

## 交接给排版 Skill

用户确认内容后保存：

- `output/<company>-<role>/resume.md`
- `output/<company>-<role>/resume.json`

然后调用 `resume-layout`。未确认的草稿不得直接进入最终 PDF。
